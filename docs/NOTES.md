## 9. 2026-09-14 晚间四项：「豆包明明答了，软件却说超时」

### ① 根因：豆包聊天页是**虚拟滚动列表**，一切「数条数」的判据都是废的

dump 页面快照后发现：对话用到第 13 轮时，**DOM 里只挂着 3 轮消息**（3 用户 + 3 AI）。
豆包只保留最近几轮在 DOM 里。

旧代码判「豆包开始回答了没有」用的是：

```python
n_ai = self._count_ai_messages()      # AI 气泡条数
if n_ai > before:                     # 比发送前多一条才算「开始回答」
```

**条数被钉死在 3，这个条件永远不成立** → 代码从不读取回答 → 死等 22 秒报
「豆包迟迟没有开始回复」。而那时豆包的回答早就完整地摆在页面上了
（快照里甚至还带着「重新生成」按钮）。用户看到的就是
「每次都查词失败，可豆包明明已经回复了」。

更坑的是 `_wait_send_effect`（判「发出去了没有」）也在数条数 → 时而误判 True、
时而误判 False。**误判成没发出去时会 `box.fill("")` 清空输入框重来** ——
这一清空把已经挂进输入框的**截图一起丢掉了**，重发的是一条纯文字消息，
豆包只能回「请上传包含美剧英文字幕的截图」。这就是
「提示词发过去了但截图没发过去」的来源。

**改法：判据全部改成「轮次 ID」，不看条数。**

| 要判断的事 | 旧（废） | 新 |
| --- | --- | --- |
| 消息发出去了没有 | `消息条数 > 发送前` | 出现了**发送前没见过的轮次 id**（集合差集） |
| 豆包开始回答没有 | `AI 条数 > 发送前` | 那条新轮次下挂出了非空 AI 正文 |
| 补充判据 | — | 输入框被清空（豆包发送后必定清空） |
| 重试时 | `fill("")` 清空重来（**连图一起丢**） | 保留原文，只在缺图时补挂 |

`MSG_SNAPSHOT_JS` 一次读回页面全部消息（按 `data-message-id` 分组）。

> ⚠️ **别改成「id 比发送前最大值更大」** —— 真机实测翻过车。豆包的
> `data-message-id` **不是严格单调递增的**：同一轮里用户气泡、AI 气泡、附件
> 各挂各的 id，大小还会乱序（实测同一轮出现 `…208578 / …208834 / …210882`）。
> 用「更大」当主判据会漏检 —— 消息明明发出去了（输入框都被清空），却一个
> 「新轮次」都找不到，白等 20 秒报超时。所以主判据必须是**集合差集**，
> 「更大」只作补充（两者取并集）。

> 附带一个坑：**DOM 里消息顺序是乱的**（虚拟列表回收节点会重排，
> 实测顺序是 `[轮次C用户, 轮次A用户, 轮次A的AI, ...]`），
> 所以 `ai[ai.length - 1]`（取最后一个节点）拿到的不一定是最新回答 ——
> 只能按 ID 大小挑。

> 还有一条：**基准（发送前的 id 集合）必须取稳**。要求「连续 3 次读到的
> 集合完全相同」才收工（约 1 秒）。复用对话时页面会分几拍才渲染完历史消息，
> 基准取早了会把历史轮次误认成新消息，拿到上一轮的旧答案。

失败快照现在还会多存一份 **`.json`**（轮次数、每轮 ID、每轮 AI 长度、输入框状态），
以后再出问题一眼就能看出症结，不用再写脚本解析 1MB 的 HTML。

### ② 提示词过去了、截图没过去

两条防线：

1. `set_input_files` 会**静默失败**（file input 被框架替换 / 页面重渲染时都不报错）。
   现在上传后校验「页面上的 blob 预览图数量增加了没有」，没增加就重传一次；
   还不行就**明确报错**，绝不发一条没有图的纯文字消息；
2. 发送重试**不再清空输入框**（旧代码的 `fill("")` 会连图一起丢掉），
   重试前会检查图是否还在，不在就补挂。

### ③ 浮窗写着「再按一次【N】关闭」，按了却不关

根因：出错时的浮窗用 `force_idle_after=True` 把状态机直接退回 `IDLE` ——
可浮窗角上的提示还写着「再按一次关闭」。于是用户按 N 时，状态机认为
「现在空闲，那就开始新查词」，把旧浮窗顶掉了，看起来就是「按了不关」。
**现在错误浮窗也走 `SHOWING`**：浮窗只要显示着，下一次按键就是关掉它
（关掉之后再按一次才是重试）。

### ④ 触发键 空格 → M → **N**

M 在 MPV / IINA / VLC / 网页播放器里都是**静音**开关，按一次查词声音就没了
（用户反馈「m 键不好用」）。N 在常见播放器里没有默认绑定，副作用最小。

### ⑤ 打包元数据跟着对齐（顺手）

* `doubao_lookup.spec` 里的版本号原来是**手写的 `"1.1.0"`**，`config.VERSION`
  升到 1.2.0 之后访达「显示简介」还写 1.1.0。现在 spec 用正则从 `config.py`
  读 `VERSION`，单一数据源，不会再对不上。
* `NSAccessibilityUsageDescription` / `NSInputMonitoringUsageDescription`
  还写着「用于监听空格键」——系统那一次授权弹窗里会显示给用户看。已改成
  「用于监听你按下的触发键（默认 N）」。
* `hotkey.py` 顶部 docstring 也还停在「触发键默认是 **M**」，一并改正。

### 顺手修掉的两个真 bug

* `doubao.py` 用了 `re.fullmatch` 却**从来没 `import re`** —— 内容短于
  `MIN_ANSWER_CHARS` 时抛 `NameError`，而这个异常被轮询循环的
  `except Exception` 静默吞掉（只写 DEBUG 日志），表现为「原地打转直到超时」。
* `_is_profile_locked` 从未定义，启动失败时恒抛 `NameError`，把真正的错误盖住。

## 10. 2026-09-15 凌晨：五项交互改动（浮窗位置·提示词·空格·追问）

用户要的五件事：① 浮窗出现在**上次的位置和大小**；② **所有**发给豆包的提示词都能编辑；
③ 浮窗显示时按**空格**关闭；④ 关掉浮窗后再按空格**直接播放**；⑤ **点浮窗能输入问题**、
豆包在同一对话里继续回答，回答**追加显示在浮窗里**。

> 附带一条最重要的教训：**改完源码 ≠ 交付。**
> 这一轮的源码在上一轮就已经写好了，但忘了「重新打包 → 签名 → 装到 /Applications」，
> 用户双击打开的一直是旧版，所以反馈「还是没有实现」。
> 收尾动作必须包含打包 + 安装 + **真机截图确认**。

### ① 位置与大小记忆（`settings.overlay_geo` + `overlay.fit_geometry`）

* 存的不是裸坐标，而是 `{w, h, x, y, screen:{x,y,w,h}}` —— **带上当时那块屏幕的可用区域**，
  这样换分辨率 / 插拔外接屏可以按「相对屏幕左上角的比例」平移。
* `fit_geometry()` 是**纯函数**（`(geo, w, h, screens) -> (x, y) | None`），
  所以位置换算能被单测钉死，不需要真开窗口。
* 最后一定夹紧到可见区域：**位置宁可差一点，也绝不能让浮窗消失到屏幕外。**

#### 坑：`pick_screen` 不能按「尺寸相同」猜屏幕

恢复位置时如果坐标不属于任何当前屏幕，原来的实现会去挑「和记录里尺寸相同的那块屏」。
多显示器下这是**严重误判** —— 只要另一台显示器分辨率跟主屏一样（很常见），
浮窗就会被摆到那台显示器上。实测抓到浮窗落在 `x=-680`（左边屏），主屏上完全看不见，
用户视角就是「按了没反应」。

现在的约定：**`screens[0]` 必须是主屏，兜底只认它**（`overlay._screen_rects()` 里
显式把 primary 排到最前）。回归测试覆盖了「副屏与主屏同尺寸」这个真实场景。

### ② 所有提示词可编辑（`prompt_edit.py` + `settings.py`）

以前那句自动追加的硬约束（`PROMPT_FRESH_GUARD_TEXT`，"只分析本条消息里附带的这一张图片"）
藏在代码里，用户只能接受。现在它也是 `settings.json` 里的一项（`guard_prompt` /
`guard_enabled`），编辑器里能改、也能整体关掉。

原则：**凡是会逐字发出去的文字，都必须露出来让人改**，不能藏在代码里。

### ③ 空格关浮窗（`config.CLOSE_KEY` + `hotkey.py`）

两条硬约束：

1. **空格只在浮窗显示时才有这个作用**；浮窗不在时程序对空格零干预；
2. **绝不吞键** —— 只是"顺便响应"，空格仍然原样送到播放器。

`hotkey.py` 因此改成「触发键 + 关闭键」两个键位；`SharedUiState.typing()` 为真时
两者都让路（正在输入框里打字，空格就是个空格）。

### ④ 关窗后空格恢复播放（`overlay._return_focus_to_player`）

以前浮窗关了但**键盘焦点还在我们那个看不见的窗口上**，用户按空格没反应，
得先用鼠标点一下播放器。现在 `closeEvent` / `exit_input()` 都会把焦点还给
`_prev_app`（弹浮窗前那个前台 App）。

### ⑤ 浮窗追问（`overlay` 输入行 + `app.submit_question` + `doubao.submit_text`）

* 点浮窗 → `enter_input()`：**只有这时才抢键盘**，并 `setWindowFlag(WindowDoesNotAcceptFocus, False)`
  让它能接收输入；
* 回车 / 点发送 → `_on_send()` → 立刻 `exit_input()` 把键盘还回去（等待期间仍可用空格控制播放）；
* 问题走 `DoubaoWorker.submit_text()`，**同一个豆包对话**（不新建），所以豆包看得见
  刚才那张截图和它的解释 —— 这正是追问的意义；
* 回答通过 `post_overlay_answer()` 追加到浮窗正文（`_qa_blocks` + `_render_body()`）。
* **追问不附加**「只看这张图」那句硬约束（纯文字问题会被它限制得没法回答）。

#### 坑 A（重要）：`has_overlay()` 只存在于**测试的假运行时**里

`app._overlay_visible()` 一直调 `self.runtime.has_overlay()`，但
`overlay.QtRuntime` 上**从来没定义过这个方法** —— 只有 tools 里测试用的 `FakeRuntime` 有。
于是真机每次调用都抛 `AttributeError`：

* 追问的回答**永远送不回浮窗**（用户视角 = 「输入了问题，什么都没发生」）；
* 判「浮窗还在不在」的逻辑全都走不到。

**这类"假对象有、真对象没有"的 bug，跑业务单测永远发现不了** —— 假对象太乖了。

两道防线：

1. `QtRuntime.has_overlay()` 补上；
2. `_overlay_visible()` 改成 **「不确定就当浮窗还在」**：返回 True 顶多多写一条日志，
   返回 False 却是把用户的回答直接丢进垃圾桶。代价不对称，所以只在**确定没有**时才 False。
3. 新增 `tools/test_runtime_contract.py`：用 AST 把「调用侧用到的每个
   `runtime.<方法>`」和「QtRuntime 真实方法表」逐一比对。有了它，
   坑 A 这类问题一秒都活不下来。

#### 坑 B：`isVisible()` 和 `grab()` 都发现不了"浮窗被盖住"

排查时反复遇到「日志说浮窗在、`isVisible()` 也是 True、`grab()` 也画得出内容，
但屏幕截图里就是没有」。经验：**界面类的 bug 不要只信程序自己的说法**，
要去问窗口服务器。`tools/probe_window_layer.py` 用 Quartz 读真实窗口层级：

* `layer=25`（`NSStatusWindowLevel`）= 正确浮在别的 App 窗口之上；
* `layer=0` = 已经退化成普通窗口，会被前台窗口盖住。
